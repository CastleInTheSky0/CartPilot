## 3. 首版范围

### 3.1 支持范围

- Windows 本地 Electron 应用及安装包，个人使用；桌面运行不要求另装 Node.js 或启动命令行服务。
- 单一商品目标、通用规格、数量、店铺要求、人民币预算及开售时间。
- 多个不同商品的独立任务同时运行，各自保存进度与订单记录。
- 同一购买目标配置多个平台或同一平台的多个候选商品链接。
- 创建任务时选择跨平台合计数量或每个平台独立数量，按进度完成相应范围的停止。
- 通过接入的普通 Chrome 标签页识别商品、预选规格、监控入口、推进结账和核对订单。
- 提供自动提交与人工确认两种模式；新建任务时不预选且必须选择。自动提交符合约束即可下单，无需逐单确认；人工确认在提交订单前等待确认。登录、验证码、支付验证和网页无法完成的步骤通过明确提示交给用户。
- 保存配置、计划、运行记录、访问限制、人工接手原因与订单提交结果。
- 使用模型辅助准备，不让模型响应时间成为每次定时点击的前置条件。

### 3.2 网页能力边界

首版自动执行普通全款、单种商品订单和已完成预约的抢购。定金尾款、分期、以旧换新、复杂套餐、多商品拼单及依赖优惠资格的条件流程，识别后提示用户接手，后续逐类适配。普通单价减免可按页面已明确展示的实际订单总额核对，不推测尚未到账的优惠或补贴。

抖音仅处理网页可以继续的购买流程。只支持 App、直播间、扫码或移动端跳转的商品，应在准备阶段显示原因和人工入口，避免到开售时才暴露。

新增网站先通过内部适配器扩展。首版不要求安装来源不明的第三方脚本，也不承诺通过统一按钮识别即可完成所有商城流程。

## 4. 任务与商品模型（建议）

### 4.1 购买任务

每个任务保存：任务 ID、名称、商品目标、数量模式、数量配额、预算、候选渠道、开售计划、执行模式、准备结果、运行状态和历史。每次执行生成独立的运行 ID，任务已下单进度、未决占用与总预算累计跨运行保留，不覆盖旧提交证据。

同一任务可以产生多笔订单，进度按有效订单里的实际商品数量累计，不能仅累计订单笔数。单笔购买数量与整个任务的目标数量分开配置。不同商品通过多个独立任务表达并可同时运行，运行并发由浏览器和平台资源约束。

已确认支持两种模式，创建任务时必须选定：

| 模式 | 配置方式 | 停止规则与示例 |
| --- | --- | --- |
| 跨平台合计数量 | 指定整个任务的目标数量，各平台共同完成 | 目标 3 件，京东下单 1 件、天猫下单 2 件后，全部平台停止新增购买 |
| 每个平台独立数量 | 对每个启用平台分别指定目标数量 | 京东 2 件、天猫 1 件；京东完成后只停止京东，天猫继续完成自己的目标 |

同一平台的多个店铺或链接共享该平台配额。规格和数量必须满足平台实际规则，遇到限购或资格限制应显示原因并暂停相应购买，不通过额外账号绕过。

已确认减量规则：每个任务可选择是否允许减量和分多笔购买，默认关闭。关闭时保持每笔设定数量，剩余额度、库存或页面限购不足一笔时暂停相应候选；开启后可减少本次数量，分多笔完成原目标，仍满足规格、预算和平台限购。例如目标 3 件、单笔 2 件，关闭时剩 1 件暂停，开启时可按 2＋1 完成。是否开启不改变任务总目标，也不影响按固定单笔数量创建多笔订单的能力。

生成有效订单号并核对商品与数量后计入已下单数量，包括待支付订单。已确认恢复规则：订单后来取消、关闭或支付超时，保留原任务进度和历史，不因订单失效自动回收数量或预算用于补买。需要再买时由用户另建购买目标；新运行 ID 或继续原任务均不能清零原进度。

### 4.2 商品与候选渠道

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| 商品目标 | 名称、商品类别、通用规格 | 规格为键值结构，如尺码、颜色、套装、容量、版本 |
| 数量计划 | 合计或分平台模式、目标配额、单笔数量 | 正整数；任务目标与单笔数量分开，分平台模式由同平台候选共享额度 |
| 渠道候选 | 平台、规范化详情 URL、商品 ID、SKU ID、店铺、规格映射 | 不同平台的同一商品可以有不同 SKU 和规格文本 |
| 价格约束 | 币种、每件最高价、任务总预算 | 首版人民币；金额按整数“分”计算；全部平台和多笔订单共享任务总预算，最终应付金额含运费 |
| 开售计划 | 含时区的开售时间、最长运行时间、刷新策略 | 各候选允许独立开售时间 |
| 执行计划 | 页面证据、定位方式、准备时间、版本 | 页面或配置变化使相关计划过期 |
| 运行结果 | 各平台已下单量、未决量、执行预留量、提交记录、订单号、结果证据 | 区分部分完成、目标完成、待支付和结果未知 |

标题相似不能单独证明是同一商品。执行前须核对详情页商品身份、SKU 或规格、数量及用户填写的店铺要求。

### 4.3 创建与准备流程

1. 用户粘贴详情页链接，或在已接入标签页选择“读取商品”。
2. 本地适配器读取可见商品、规格、店铺及购买方式；需要时调用 AI 补充结构化识别。
3. 用户确定目标规格、数量模式与配额、单笔数量、每件最高价和任务总预算、候选渠道、开售时间和自动提交设置。
4. 系统检查扩展连接、标签页、登录、页面可访问性、适配能力和未决订单。
5. 准备成功后保存任务计划；缺失信息显示具体原因，不能自动猜测规格或预算。
6. 用户启动任务后按计划执行；重要配置变更要求重新准备。

继续已停止或部分完成的任务，只执行原目标的剩余数量；不得因为生成新运行 ID 而清零已下单量。需要购买新一批时，通过创建或复制任务明确新的目标，旧历史保留。运行中不直接修改数量模式、规格或预算；停止并重新准备时仍须核对已有订单及占用。

建议保留平台搜索入口。首版商品选择以详情页和已接入标签页为主，不依赖 AI 全网搜索即可启动。

## 5. 多平台购买、数量控制与订单结果

“发现购买入口”“取得结账资格”“订单已创建”应显示为不同阶段。

- 各候选可以并行观察；满足数量、预算与账户资源约束时，不同平台可以分别推进购买。某平台成功一单不自动结束整个任务。
- 跨平台合计模式由所有候选共享数量额度，达到目标后停止该任务的新增购买动作；分平台模式只停止已完成配额的平台，其他平台继续。
- 只有识别到订单确认及有效的唯一订单号，并核对商品与数量后，才记为“订单已创建”并累计实际件数；待支付订单同样计入。
- 同一订单按平台和订单号去重，重复读取确认页不重复累计。订单证据须关联本次购买意图与目标商品，不能把无关的历史订单算入进度。
- 每个候选进入可能生成订单的阶段前，先以事务预留对应数量与预算；合计模式满足“已下单量＋未决占用量＋执行预留量不超过任务目标”，分平台模式对每个平台分别成立。
- 进入人工提交交接或触发订单提交前，先保存提交意图；超时、断线、崩溃及结果未知均不自动重复同一次提交，保留相应数量和预算占用。
- 某次提交未知不意味着所有平台都必须停；其他候选只有在其配额、任务总预算和账户资源均不受未决记录影响时才可继续。
- 如果尚未触发可能生成订单的动作，且能够确认当前渠道失败、无未决副作用，才允许释放预留或转交候选。平台之间的独立配额不能自行挪用。
- 支付状态单独显示，不能把“进入结账”或“点击提交”显示成购买成功。
- 无法读取订单号时标为“结果待核对”，不算已下单成功，也不释放占用，由用户在平台检查后处理。

建议将资源管理拆为数量与预算预留、单次提交记录、标签页占用锁、账户结账资源锁与平台访问限制。提交记录按购买意图持久化，允许任务按目标创建多笔不同订单，同时防止同一次意图重复执行。同一账户的购物车或结账状态可能相互影响，不能可靠隔离时须串行。

多个任务的配额和预算独立，浏览器标签页、账户结账资源及访问限制由全应用统一协调。某任务等待验证、冷却或核对订单时，其他任务能否继续取决于共享资源，不应将无关任务全部暂停。

已确认预算采用每件最高价＋任务总预算：每件按页面可核对的优惠后商品单价判断，全部平台、多笔订单共享任务总预算。累计按订单显示的优惠后最终应付总额计算，包含运费且不重复计入；后续退款、返现不预先抵扣。已下单金额（含待支付）、未决金额和执行预留金额合计不得超过任务总预算。单价或应付总额不明确、额度不足、目标只部分完成或部分平台等待验证时，应显示具体状态，不能为了凑数量擅自提高预算、修改规格或突破限购。具体预留机制属于技术实现建议。

重复配置同一链接、SKU、账号及购买目标时给出合并或重复购买提示；复制任务不得复制已授权的运行状态。订单记录修改须保留审计历史。

## 6. 浏览器与登录体验

- Electron 展示本地工作台；商品页面在普通 Chrome 中打开并执行。
- 正式路径仅有安装扩展、授权连接、选择标签页、检测状态，不再显示“助手独立窗口”切换。
- 复用官方 Playwright Extension 和已验证的连接桥；首版正式支持 Windows 上的普通 Chrome，其他浏览器与操作系统后续另行验证。
- 只控制用户明确接入的标签页与有可追溯来源的弹窗；多任务不得争用同一标签页。
- 断开时停止相关自动执行、释放控制并保留浏览器页面；重新连接后不能沿用旧标签页 ID 或旧登录结论。

工作台顶部应常驻扩展连接摘要；渠道列表明显显示以下三项，不能混成一个“已连接”：

| 状态 | 显示内容 |
| --- | --- |
| 扩展连接 | 未连接、连接中、已连接、连接异常 |
| 标签页 | 未接入、已接入（页面标题）、页面已变化或关闭 |
| 商城登录 | 已登录、需要登录、待验证、暂无法确认；附检测时间 |

登录检测沿用只读检查与过期机制；当前默认每 10 秒检测，45 秒过期。未知不能当作已退出，也不能因为扩展连接成功就显示已登录。提供“重新检测”和定位接入页面的入口。

删除独立窗口代码时保留用户原有登录资料；不得借迁移删除 Chrome 资料、复制 Cookie 或清空访问冷却记录。

## 7. AI 职责与约束

### 7.1 已确认的分工

AI 在开售前协助理解商品、规格和页面，生成结构化执行建议；页面变化时可再次辅助。本地执行器按时间和可验证规则执行，核心购买链路不要求每次点击都调用模型。

### 7.2 首版能力与实现建议

- 将不同候选页面的规格映射到统一购买目标，并展示不确定项。
- 分析脱敏页面快照，建议受限操作计划和页面适配调整。
- 解释失败、冷却、登录异常和人工接手原因。
- 缓存可复用的准备结果，展示模型、耗时、调用次数和可获知的用量。

上述缓存和展示细节属于实现建议；自然语言创建任务、截图上传、视觉模型与专门的 AI 费用分析页面不在首版范围，具体以 Trellis PRD 为准。

### 7.3 执行边界

模型输出须通过 schema 与本地权限检查。定位器必须唯一、页面身份必须匹配，提交前仍需重新核对真实页面。

模型不能修改既定数量或预算、清除订单锁、解除冷却或把未识别结果宣称成功。网页内容只作为数据，页面中的指令不能扩大工具权限。工具层不提供任意终端命令、任意脚本执行或无约束网络访问。

建议平台访问、选择规格和点击动作复用 Playwright；应用只补充受控工具与业务约束，不另造一套 AI 浏览器运行时。

### 7.4 模型配置与数据

已确认支持 OpenAI 兼容 Chat Completions 和 Anthropic 原生 Messages 两类接口，由用户自备 API Key、接口地址和模型名。设置页可保存多份配置、切换默认配置并逐个测试连接，不在产品中写死某个模型。首版“OpenAI 兼容”按 Chat Completions 验收，其他 API 协议不自动纳入支持范围。

用户补充首版供应商清单：Gemini、DeepSeek、Kimi、豆包（火山方舟），并保留 Anthropic 原生接口和自定义兼容接口。供应商与接口协议分开配置；建议新增四家复用 Chat Completions 适配层，按供应商处理端点、模型标识、参数和能力差异。Gemini 亦有原生 API，但其全部专有功能不自动进入首版。各家的配置、连接与最低能力须分别验收，不能以通用输入框存在或另一家测试通过代替；官方核对依据见 PRD 的 R07。

两类接口均以文本页面分析和生成经本地 schema 校验的结构化计划作为最低能力，分别验证连接与计划结果，不能只凭连接成功就标为全部支持。首版不要求原生工具调用、视觉输入或供应商专有结构化输出功能；具体供应商与模型按实际配置测试。建议任务保存所用模型配置引用，变更默认配置不在运行中静默切换模型。

默认仅发送当前任务所需的脱敏商品文本和页面片段；Cookie、访问令牌、密码、收货地址和支付内容不发送给模型。首版不上传截图。密钥由主进程借助操作系统存储能力保护，渲染界面和日志不保留明文。

支持调用超时、有限重试、调用频率与每任务用量上限。展示调用次数、供应商可提供的 token 用量；只有已知计费信息时显示估算费用并标为估算，不把估算当成供应商账单。模型不可用时，已准备且仍有效的本地计划继续运行；需要模型重新识别的页面暂停并提示用户。

## 8. 调度、冷却与恢复

- 沿用 DOM 读取与整页刷新分离、导航节流和网络退避；多个任务共享平台访问预算。
- 淘宝与天猫沿用同一访问组。403／429／541、验证码与页面异常按已有规则暂停或冷却，不因多任务、换渠道或重启绕开。
- 当前基线：日常刷新默认 120 秒，开售窗口默认 30 秒；429 尊重 Retry-After，403／541 至少 10 分钟并等待人工检查。迁移时不降低已有保护。
- 启动、停止、等待接手、冷却、准备过期、提交中、订单已创建和结果未知均须有明确状态。
- 建议应用重启后恢复任务配置、冷却和提交记录，任务进入待复核状态，不自动重新提交。
- 建议运行任务时可最小化到系统托盘并保持运行；退出、休眠、断网应明确提示执行影响。关机期间不执行本地任务。
- 本机时间影响开售调度，界面显示时区与时间检查提示；运行中停止任务应取消定时器和后续动作，但保留已产生的提交证据。

## 9. 桌面工作台（建议）

主要页面为任务列表、任务详情、浏览器连接、模型设置、订单与运行记录。保留显眼的全局停止入口。

任务列表展示商品、规格、数量模式、已下单量／目标量、预算进度、开售倒计时、准备结果及当前阶段。任务详情按平台展示目标、已下单、待核对和执行预留数量，以及登录、库存入口、冷却、结账资格、异常和接手入口。

部分平台完成而其他平台仍运行时，任务显示“部分完成／继续执行”；全部所需配额完成才显示“目标已完成”。单笔订单已创建和整个任务完成分别展示。

人工接手通知必须包含任务、平台、原因和对应页面；用户处理后由程序重新读取页面，不能仅凭点击“继续”就推定问题解决。

普通用户流程不要求填写 CSS 选择器。高级适配作为诊断入口，作用范围限定在具体平台与页面版本，仍经过相同的订单核对。

## 10. 本地数据与迁移

建议使用 SQLite 保存任务、数量与预算配额、候选、运行、事件、多笔订单提交、访问限制及迁移版本。具体框架选择与 Electron 原生模块打包先完成验证。

- 数据目录迁到 Electron 用户数据目录；首次迁移先做本地备份，验证成功再切换读写。
- 旧 workspace 转换为一个购买目标及多个候选；不一致的规格、数量或预算作为迁移冲突展示，不能合并猜测。
- 旧任务按原有数量目标迁移为跨平台合计模式，增加多平台购买能力不自动增加旧任务的购买数量；新任务显式选择数量模式。
- 保留原配置、日志、未决提交和冷却；无法匹配的历史提交至少阻止自动执行并提示核对，不能默默忽略。
- 旧 managed 模式迁到“待连接扩展”，不自动启动独立窗口，也不复制其登录会话。
- 迁移应可重复检测、可回退；数据库损坏或迁移失败时停止购买动作并给出恢复路径。
- 应用采用单实例机制，避免两个进程同时操作相同数据与浏览器。

## 11. 工程与质量要求

详细约定见 [工程与代码规范](./engineering-standards.md)，由仓库根目录 `AGENTS.md` 固化为后续开发约定。

- 延续 TypeScript；按主进程、preload、renderer 和共享契约分层，再按功能拆模块。
- 统一命名、缩进、格式、模块导入、错误处理、异步取消和组件拆分；采用 EditorConfig、Prettier 和 ESLint 的成熟方案。
- 新写或迁移的手写 TS、TSX、JS、CSS 默认不超过 400 个物理行，空行和注释计入；不得通过压缩成一行规避。
- 锁文件、生成代码、构建产物、测试快照及文档不受代码行数限制；测试逻辑仍遵守拆分要求。
- ESLint 规则与行数检查落实约束；老大文件按迁移阶段逐步消除，完成迁移时清零超限。
- 当前已落地行数检查和现有文件禁止增长的临时基线，并纳入构建前检查；Prettier、ESLint CLI 及完整组合检查在迁移工具链阶段接入，不视为当前已运行通过。
- 跨进程通信、模型输出与持久化数据采用统一 schema 校验。
- 单元与集成验证使用隔离数据和离线商城页面；真实页面验证默认只读，不因测试触发真实购买。

## 13. 开发默认方案与后续决策

首版的范围、执行方式、AI 分工、任务并行、两种数量模式、计数标准、复杂订单边界、模型接口、四家供应商与最低能力、交付对象、预算、减量、取消与提交默认值已完成访谈，结论见 D01–D19。

Q01–Q05 均已确认并回填；当前没有剩余待用户确定的需求项。常规实现细节可沿用工程建议，不因澄清完成而自动启动实施：

- 已确认：保留自动提交和人工确认两种任务设置；创建任务时必选且不预选，未选择不能完成创建或启动，启动后按已选设置执行，支付与身份验证由用户接手。
- 已确认：单笔数量不得超过剩余额度；减量默认关闭，任务明确开启后才可按剩余额度或页面可购买数量减量并分多笔购买，不修改目标或突破预算、平台限购。
- 已确认：订单取消、关闭或支付超时不自动重新购买；任务继续保留原订单进度和历史，需要再买时由用户另建购买目标。
- 模型调用限额、脱敏、账户串行、恢复、日志和迁移按文中约束落实，具体阈值在设计与实现阶段配置。
- 第三方插件市场、公开分发、自动更新、其他桌面系统与浏览器作为后续扩展方向。

技术方案里仍需验证的兼容性属于实施工作，先完成最小 Electron 安装包与现有扩展桥验证，再推进完整重构。当前交付包括需求、迁移和工程规范文档，以及格式配置和行数检查；尚未安装新框架、替换业务代码或改变运行中的浏览器连接。
