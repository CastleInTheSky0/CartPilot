## 1. Goal

把现有面向特定手机的助手，改为 Windows 自用的通用实物商品抢购应用。Electron 承载工作台，通过官方扩展连接普通 Chrome；AI 负责提前准备和页面变化辅助，本地程序负责定时执行。

支持多个不同商品任务同时运行。每个任务可以在多个平台实际购买，根据所选数量模式停止，而非统一在第一笔订单成功后结束。

## 4. Requirements

### R01. Windows 桌面与扩展接入

- 交付可独立启动的 Windows Electron 安装包，供用户自己使用。
- 应用内提供扩展安装入口、连接授权、标签页选择、接入和断开操作。
- 商品操作在明确接入的普通 Chrome 页面执行，删除助手独立浏览器模式的相关代码和界面。
- 断开停止相关自动执行，释放控制并保留普通 Chrome 页面。
- 迁移保留原有数据与登录资料，不通过复制 Cookie 接入普通 Chrome。

### R02. 通用商品与五平台

- 商品模型移除特定手机名称、颜色和容量枚举，支持规格键值、数量、平台商品身份和店铺要求。
- 五个平台通过明确的适配边界复用现有能力，保留已有主备链接能力。
- 以商品详情页和明确接入的标签页作为购买目标来源，提交前核对真实商品、SKU／规格、数量、店铺要求与价格。
- 只支持网页可以推进的流程；必须唤起 App 或无法识别的页面明确交给用户。
- 同平台已有主备候选共享相应数量限制，不增加商家批量发现或商品批量采集功能。

### R03. 多个商品任务并行

- 不同商品可创建独立任务，同时运行，分别设置数量模式、预算、开售时间并保存状态。
- 标签页占用、账户结账资源和平台访问限制统一协调，冲突资源排队。
- 某任务等待验证或订单核对时，其他任务能否继续取决于共享资源，不能固定全局停止。
- 每个任务可停止和接手，保留运行与订单记录。

### R04. 两种数量模式

| 模式 | 配置 | 预期行为 |
| --- | --- | --- |
| 跨平台合计 | 任务目标 N 件，多平台共同完成 | 目标 3 件，京东 1 件＋天猫 2 件后，所有候选停止新增购买 |
| 每个平台独立 | 分别设置各平台目标 | 京东 2 件、天猫 1 件；京东完成只停止京东，天猫继续 |

- 以商品件数累计，不以订单笔数代替；一笔订单多件应累计实际件数。
- 并发执行须预留数量，未决提交保留占用，防止候选同时消耗同一剩余额度。
- 继续原任务须保留已有进度，不因新运行 ID、崩溃或重启而清零。
- 每个任务可选择是否允许自动减量并分多笔购买，默认关闭。默认每笔保持设定数量；剩余额度、库存或页面限购不足一笔时，暂停相应候选并显示原因，不自动改变单笔数量。
- 明确开启后，可按剩余额度和页面可购买数量减少本次数量，分多笔完成原目标；不增加目标、不改规格、不超预算或绕过平台限购。目标 3 件、单笔 2 件时，关闭则剩 1 件暂停；开启则可按 2＋1 完成。（Q02 已确认）
- 已生成有效订单号并核对通过的订单，后来取消、关闭或支付超时，仍保留原任务已下单进度和历史；不因这些状态变化自动回收额度并补买。需要再买时，由用户另建购买目标。（Q03 已确认）

### R05. 订单结果、预算与幂等

- 平台生成有效订单号，且目标商品和数量核对通过后，记录为订单已创建并计入进度；待支付也计入。
- “有购买入口”“进入结账”“已点击提交”“订单已创建”“任务目标完成”和“已支付”分别表达。
- 同一订单重复读取不重复计数；每次购买意图保留持久化提交记录，结果未知不盲目重复提交。
- 允许按任务目标创建多笔不同订单，避免沿用“全应用永远只允许一单”的旧限制。
- 每个任务设置每件最高价与任务总预算；每件按可核对的优惠后商品单价判断，全部平台和多笔订单共享总预算。
- 任务预算按订单显示的优惠后最终应付总额计算，包含运费且不重复计入；后续退款、返现不预先抵扣。已下单金额、未决金额和执行预留金额合计不得超预算，待支付订单也占用预算；单价或应付总额无法核对时不提交。（Q01 已确认）
- 订单结果未知时保留数量占用和核对入口；不能将未知结果算作已买到，也不能直接当作失败释放额度。
- 区分“从未生成订单且已确认无副作用的失败”和“已生成有效订单后取消或关闭”；后者保留累计下单记录，不自动释放数量或预算用于补买。

### R06. 自动执行与人工接手

- 自动执行普通全款、已完成预约的网页抢购流程。新建任务时必须明确选择“自动提交／人工确认”，不预选；未选择不能完成任务创建或启动。（Q04 已确认）
- 自动提交模式下，符合商品、数量、预算与平台规则即可提交订单，无需逐单确认；人工确认模式在提交订单前等待用户确认。选定模式随任务保存，不能由 AI 推断或更改。
- 登录、验证码、支付验证、定金尾款、分期、以旧换新、复杂套餐等由用户接手。
- 接手提示明确任务、平台、原因和对应页面；继续执行前重新读取真实页面。
- 不自动代替用户完成支付。

### R07. AI 辅助与模型配置

- AI 在开售前识别商品、规格和页面并准备计划；页面变化时再辅助分析。
- 到点执行由本地程序完成，核心步骤不依赖每次点击前调用模型。
- 支持 OpenAI 兼容 Chat Completions 和 Anthropic 原生 Messages 两类接口；用户填写供应商、API Key、接口地址和模型名，保存多份配置、切换并逐个测试连接。（Q05 已确认）
- 首版供应商清单明确包含 Gemini、DeepSeek、Kimi、豆包（火山方舟），并保留 Anthropic 原生接口和自定义兼容接口。四家分别验证配置保存、切换、连接与最低能力，不以存在一个通用地址输入框代替供应商验收。（D19 已确认）
- 两类接口的最低能力均为文本页面分析与生成符合本地 schema 的结构化计划。连接可用与计划校验通过分别验证，不以接口可连通推定模型具备所需能力。
- 模型输出经过结构化校验和本地购买约束检查，不能自行修改预算、数量、锁或冷却。
- 复用成熟模型 SDK 与现有浏览器能力，密钥及必要页面数据按既有工程约束处理。

| 接口类型 | 首版验收范围 | 最低能力 |
| --- | --- | --- |
| OpenAI 兼容 | Chat Completions；供应商地址、Key 与模型名由用户配置 | 脱敏文本输入、页面分析、可经本地 schema 校验的结构化计划 |
| Anthropic 原生 | Messages；接口地址、Key 与模型名由用户配置 | 同上，作为独立接口适配验收 |

供应商与模型是否可用按具体配置测试，不承诺所有声称兼容的服务均具备所需能力。首版不要求原生工具调用、视觉输入或供应商专有结构化输出功能；其他 API 协议不自动纳入验收。

供应商与协议分别建模。基于官方资料，当前技术建议是让新增四家复用 Chat Completions 适配层，分别处理地址、密钥、模型标识、参数与能力差异；模型请求直接发送到所配置的供应商。Gemini 的原生 API 属于另一种接入选择，不因支持 Gemini 就自动扩展到其全部原生功能。

| 必须支持的供应商 | 首版建议接入方式 | 官方核对依据 |
| --- | --- | --- |
| Gemini | OpenAI 兼容 Chat Completions | [Google 官方兼容示例](https://github.com/google-gemini/cookbook/blob/main/quickstarts/Get_started_OpenAI_Compatibility.ipynb) |
| DeepSeek | OpenAI 兼容 Chat Completions | [官方首次调用说明](https://api-docs.deepseek.com/zh-cn/) |
| Kimi | OpenAI 兼容 Chat Completions | [官方 Chat Completions 文档](https://platform.moonshot.cn/docs/api/chat) |
| 豆包（火山方舟） | Chat Completions，处理方舟配置差异 | [官方 SDK 调用示例](https://github.com/volcengine/volcengine-python-sdk/blob/master/volcenginesdkexamples/volcenginesdkarkruntime/completions.py) |

以上为 2026-10-15 官方资料核对结果与技术建议，不代表本项目已经完成模型接入或真实连接验证；实际模型标识与能力在用户具体配置下检测。

### R08. 状态可见与既有能力保留

- 在明显位置分别显示扩展连接、标签页接入、商城登录状态及检测时间。
- 登录未知、过期或页面验证时清晰显示，不能将“扩展已连接”等同于“商城已登录”。
- 各任务与平台显示已下单量、目标量、待核对状态和异常原因，部分完成时仍可看到其他平台继续运行。
- 保留已有京东登录修复、DOM 读取、导航节流、退避、共享访问组和持久化冷却。
- 迁移保留旧配置、历史提交和冷却，不静默丢弃未决记录。

### R09. 工程约束

- 采用 Electron 常见的 main／preload／renderer 分层，按业务职责拆模块，遵守项目工程规范。
- 保持 TypeScript strict、统一命名与格式、明确跨进程契约和模块依赖边界。
- 新写或迁移的手写代码默认每文件不超过 400 个物理行，含空行与注释。
- 现有 4 个超限文件按既有基线禁止增长，迁移完成后拆分并移除临时基线。
- 使用现有成熟框架和推荐规则，避免自造状态机、构建系统、模型 SDK 或浏览器协议。
- Electron 已确认；electron-vite、electron-builder、XState、Zod、AI SDK、SQLite 等仍属于技术选型建议，不能以选型为由新增产品功能。

## 5. 不在本任务范围

- 新商城平台、macOS／Linux、其他浏览器的正式支持。
- 多账号管理、账号池、代理池、验证码绕过或规避平台限制的能力。
- App、直播间或移动端专用自动化，自动支付及复杂订单自动处理。
- 第三方插件市场、公共发布、自动更新服务、云端托管执行或分布式抢购。
- 自然语言创建任务、全网找货、批量采集、跨店铺比价或商家发现。
- 截图上传、视觉模型能力与专门的 AI 费用分析页面；这些仅在旧文档中作为建议出现，未确认为首版必需功能。
- 当前不开展 UI 全面重设计，不更换包管理器，也不增加无关基础设施。

以上范围外项目不自动进入待办，也不因为实现库支持便默认交付。
